Non-Blocking I/O { poll() }

The server in src/server.cpp is a single thread that serves many clients with O_NONBLOCK + poll(). Portable multiplexing — no thread pool, no epoll/kqueue.

01

The Blocking Problem

A blocking accept(), read(), or write() parks the whole process until that one syscall finishes. With one thread:

  • accept() waiting for client B means client A gets no ticks.
  • read() stuck on a slow client stalls everyone else.
  • A full send buffer on one socket blocks the broadcast loop.

For a market-data feed that fans out ticks to N clients, blocking I/O requires a thread per connection — which this project deliberately avoids.

02

O_NONBLOCK

Mark the fd so syscalls return immediately instead of sleeping:

socket_opts.hpp
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

Then accept / read / write either make progress or fail with errno == EAGAIN or EWOULDBLOCK: not ready — try later. That is not a fatal error; wait until poll reports the fd is ready.

In src/server.cpp: listen socket and every accepted client are non-blocking. The client uses blocking connect + poll with a timeout for read readiness.

03

poll()

poll() watches many fds and sleeps until at least one is interesting (or the timeout expires):

poll sketch
struct pollfd {
    int   fd;
    short events;   // what you care about: POLLIN, POLLOUT, ...
    short revents;  // what happened (filled by kernel)
};

int n = poll(pfds, nfds, timeout_ms);
FlagMeaning
POLLINReadable — data, or listen socket has a pending accept
POLLOUTWritable — send buffer has room
POLLERR / POLLHUPError or hangup — drop the client

Level-triggered: if data is still unread, POLLIN stays set on the next poll. Drain until EAGAIN, then wait again.

04

Server Loop

src/server.cpp — one thread, dual deadlines (tick rate + heartbeat interval):

  1. Build a pollfd array: listen fd (POLLIN) + each ClientSession (POLLIN, plus POLLOUT when has_pending()).
  2. poll(...) with timeout = min(ms until next tick, ms until next heartbeat).
  3. Listen readable → accept in a loop until EAGAIN; wrap in ClientSession.
  4. For readable clients → on_readable() (drain/discard inbound; detect close).
  5. For writable clients with pending outbound → flush() until EAGAIN.
  6. When tick deadline fires → TickGenerator::next(), enqueue to every session (even if zero clients — generator still advances).
  7. When heartbeat deadline fires → enqueue HEARTBEAT to every session.
src/server.cpp (structure)
while (!g_shutdown) {
    // build pfds[] from listen_sock + clients
    int timeout_ms = min(ms_until(next_tick_at), ms_until(next_hb_at));
    poll(pfds.data(), pfds.size(), timeout_ms);

    accept_until_eagain();           // new ClientSessions
    for (each client) handle I/O;    // on_readable / flush
    if (tick due)  broadcast tick;   // generator.next() → enqueue_tick
    if (hb due)    broadcast hb;     // enqueue_heartbeat
    drop_dead(clients);
}
05

poll vs select

  • select is limited by FD_SETSIZE (often 1024) and needs fd-bitmask rebuilds each call.
  • poll takes an array of pollfd — no fixed set size in the API, clearer events/revents model.

Either works for a handful of clients. This project uses poll as the portable choice.

06

Why Not Threads or epoll

Thread-per-client would keep clients from blocking each other, but adds mutexes around tick fan-out and complicates reasoning for a workload that is “broadcast the same bytes to N sockets.”

Linux epoll / macOS kqueue scale better at huge fd counts — overkill for this simulator.

Decision

Single-threaded poll() + O_NONBLOCK. Rejected: thread-per-client (mutex noise, harder to reason about), epoll/kqueue (portability and scope — fine for a different project at higher scale).

08

Pitfalls

✕

Busy-loop without a poll timeout

Calling poll(..., 0) forever burns a core. Use a positive timeout so idle time sleeps and tick/heartbeat deadlines still fire.

✕

Forgetting to remove closed fds

After a session dies, erase it from clients before the next poll. SocketGuard closes the fd; leaving a stale fd in poll causes spurious events or EBADF.

✕

Ignoring partial writes

send may send fewer bytes than requested. ClientSession::flush keeps an outbound buffer and out_off — only clear after the full message is sent.

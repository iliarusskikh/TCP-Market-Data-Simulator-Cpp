Latency { Measurement }

The client in src/client.cpp records inter-arrival times between consecutive TICKs and reports p50/p99 via LatencyStats in latency.hpp. This is not one-way wire latency or RTT.

01

What we measure

This project is a one-way feed: server pushes TICK / HEARTBEAT; the client does not echo. That constrains what “latency” can mean honestly.

MetricHowCaveat
Inter-arrival time (what we use) Client timestamps successive TICK receives with steady_clock; delta = gap between ticks Measures client-side spacing / jitter — not wire delay from server
RTT Would need a request/echo path Not implemented — one-way feed only
One-way via server stamp recv_time − tick.timestamp_ns Only meaningful if host clocks are synchronized — we do not assume that
Important

Inter-arrival ≠ one-way latency. A steady 10 ms inter-arrival could be perfect server pacing plus zero network delay, or slow network plus fast server — the metric alone cannot distinguish. Report it for what it is: local receive spacing.

02

Which clock

For local intervals, use std::chrono::steady_clock. It is monotonic — wall time can jump with NTP adjustments.

  • steady_clock — used in src/client.cpp for last_rx, inter-arrival deltas, and poll timeouts.
  • system_clock — wall time; fine for human logging, not for micro-intervals.

No TSC / rdtsc, cycle pinning, or calibrated CPU clocks — out of scope for this project.

03

p50 / p99 — why mean lies

Latency distributions are typically skewed: most samples are fine; a few spikes (scheduler, logging, Nagle if you forgot TCP_NODELAY) pull the mean up. A mean of 2 ms can hide a p99 of 40 ms.

  • p50 — median; “typical” experience.
  • p99 — 99th percentile; tail that matters for latency-sensitive systems.

LatencyStats::report also prints p99.9, min, and max at shutdown.

04

LatencyStats

include/latency.hpp — client-side collector. Hot path: push a nanosecond sample; report time: sort and pick percentiles.

latency.hpp + src/client.cpp
LatencyStats interarrival;

// on each TICK (not heartbeat):
const auto now = steady_clock::now();
if (last_tick_at != time_point{}) {
    const auto delta = duration_cast<nanoseconds>(now - last_tick_at);
    interarrival.add_ns(delta.count());
}
last_tick_at = now;

// at shutdown:
interarrival.report("inter-arrival");

max_ticks on the client CLI: 0 or omitted = unlimited; positive value stops after N ticks then prints stats. Inter-arrival resets across reconnects (last_tick_at cleared on reconnect).

05

Project decision

Decision

Inter-arrival p50/p99 via LatencyStats on the client, using steady_clock deltas between consecutive TICKs. Rejected: RTT measurement (no echo path), server-stamp one-way latency (requires synced clocks), TSC/hardware timestamps (out of scope).

Deliberately skipped: lock-free timestamp rings, kernel bypass, hardware timestamps, cross-host clock sync.

06

Pitfalls

✕

Calling inter-arrival “latency” without caveat

It is receive spacing on one machine — not proof of network delay. Say what the metric measures.

✕

Measuring only in Debug

Unoptimized builds inflate numbers. Use Release (-O2 / -O3) for any stats you quote.

✕

Logging inside the timed path

std::cout / formatting per tick dominates the interval you think you're measuring. Sample first; print summaries at shutdown via LatencyStats::report.

✕

Comparing host clocks without sync

Server timestamp_ns minus client now across two machines is not one-way latency unless clocks are synchronized.

Heartbeat { & client reconnect }

The server broadcasts application HEARTBEAT messages on a timer. The client in src/client.cpp treats any received message as liveness, detects silence via last_rx, and reconnects with exponential backoff.

01

Why app heartbeat

TCP can leave a half-open connection: one side thinks the socket is fine while the peer has crashed, the cable is gone, or a NAT silently dropped state. Reads may sit quiet under nonblocking poll until the OS eventually notices.

SO_KEEPALIVE exists, but defaults are often on the order of hours — too slow for a feed client that should notice a dead server in seconds.

Decision

Application HEARTBEAT message on a configurable interval (heartbeat_interval_ms in config). Rejected: relying on TCP keepalive alone — OS defaults are too slow; rejected: inventing a side-channel ping outside the binary protocol.

02

Server send / client last_rx

The server maintains a heartbeat deadline alongside the tick deadline in src/server.cpp. When it fires, every ClientSession gets an enqueue_heartbeat — same binary framing as ticks (protocol.hpp).

The client maintains last_rx. Any successfully parsed message — TICK or HEARTBEAT from recv_feed — refreshes it. Busy markets don't need spare heartbeats to prove liveness; quiet markets do.

src/client.cpp (pattern) 
// after recv_feed succeeds:
last_rx = steady_clock::now();   // tick *or* heartbeat

// poll timeout = remaining time until heartbeat_timeout_ms since last_rx
poll(&pfd, 1, wait_ms);
if (poll timed out || now - last_rx >= heartbeat_timeout_ms) {
    sock.reset();
    state = ConnState::Disconnected;
}
03

Timeout → reconnect

When silence exceeds heartbeat_timeout_ms (from config):

  1. sock.reset() — SocketGuard closes the fd.
  2. State → Disconnected; reconnect with backoff.
  3. On success, reset last_rx and resume recv_feed.

Same path on hard errors (recv_feed returns closed/error): close and reconnect. The heartbeat timer covers the silent-death case TCP doesn't surface quickly.

04

Exponential backoff

After a failed connect or connection death, the client waits before retrying. In src/client.cpp: start at reconnect_initial_ms, double each failure, cap at 5000 ms, stop after reconnect_max_retries.

src/client.cpp 
if (!connect_to_server(cfg, sock)) {
    sleep_for(milliseconds(backoff_ms));
    backoff_ms = min(backoff_ms * 2, 5000);
    ++attempt;
    continue;
}
// on success:
attempt = 0;
backoff_ms = cfg.reconnect_initial_ms;
Decision

Exponential backoff with cap and max retries. Rejected: tight reconnect loops — hammer a restarting server and burn CPU.

05

Connection states

The client tracks an explicit state machine:

StateMeaning
DisconnectedNo live socket; may be backing off between attempts.
ConnectingAttempting connect().
ConnectedReading via recv_feed; updating last_rx.

Transitions: timeout/error → Disconnected → (after backoff) Connecting → success → Connected. State is logged on each transition.

06

Project decision

Decision

Market-data only. Protocol message types are TICK and HEARTBEAT — heartbeat is a first-class binary message. Server pushes heartbeats on a timer; client owns timeout detection, reconnect, and backoff. No ORDER/ACK, no session login.

07

Pitfalls

✕

Only HEARTBEAT counts as alive

If ticks don't refresh last_rx, a healthy busy feed can look "dead" between heartbeat slots. Refresh on any message.

✕

Reconnect storms (no backoff)

Tight connect loops hammer a restarting server and your own CPU. Cap delay and retries.

✕

Relying on TCP keepalive alone

OS defaults are too slow for feed UX. App heartbeat is the primary detector.

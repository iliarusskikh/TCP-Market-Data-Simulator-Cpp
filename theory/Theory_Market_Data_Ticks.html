Market Data Ticks { synthetic generator }

Not a real exchange. TickGenerator in tick_generator.hpp invents last-trade-style updates so the project exercises protocol, poll(), and client consumption — not market microstructure.

01

What a tick is here

In this project a tick is one last-trade-style update: enough fields to exercise the wire format and fan-out, nothing more.

FieldTypeRole
msg_typeuint8_tMsgType::TICK
symbol_iduint32_tWhich instrument (numeric id from config)
priceint64_tScaled integer (micros: 1e6 == 1.0)
volumeuint32_tSynthetic size for the update
timestamp_nsuint64_tServer stamp from steady_clock

Wire layout in protocol.hpp — 25 bytes packed. HEARTBEAT is a separate 9-byte message type.

02

Scaled integer prices

Prices are int64_t on the wire (price × 106 micros), not double.

  • Determinism — fixed seed → same integer path. Float rounding differs by platform.
  • Endianness — integer swaps via host_to_net_i64 are well-defined. IEEE floats invite subtle wire bugs.
  • Production habit — money and prices are fixed-point on feeds; floats are for analytics at the edge.
Decision

Scaled int64_t prices. Rejected: double on the wire — non-deterministic across platforms and harder to serialize portably.

03

Random-walk model

TickGenerator keeps per-symbol state. Each call to next() advances one symbol (round-robin), applies a small random delta, clamps to bounds, and returns a host-order TickMsg.

tick_generator.hpp
// seed=42 from server → reproducible demos
TickGenerator generator(cfg, /*seed=*/42);

TickMsg tick = generator.next();
// price += uniform delta in [-5000, +5000]  (±0.005 at micro scale)
// volume = uniform [1, 100]
// timestamp_ns = steady_clock::now()

Toy path — no drift calibration, no vol surface, no order-flow imbalance. The goal is infrastructure, not economic realism.

04

Symbols & tick rate

config/default.conf drives host, port, symbol list, tick rate, and heartbeat interval. The server's TickGenerator walks config symbols in round-robin at tick_rate_hz.

config/default.conf
host=127.0.0.1
port=9000
symbols=1,2,3
tick_rate_hz=100
heartbeat_interval_ms=1000

Loaded at startup — change symbols or rate without recompiling.

05

Generate & broadcast

The server owns the generator. On each tick deadline it calls generator.next(), then enqueues the same wire bytes to every ClientSession via enqueue_tick.

  • One generator → N sockets (broadcast). All clients see identical ticks.
  • The generator advances on schedule even with zero connected clients — time and prices keep moving.
  • Clients only parse and measure; they do not send orders.
Decision

Server-side generation + broadcast. Rejected: per-client generators (different prices per client — unnecessary complexity), client-pull model (this is a push feed).

06

Project decision

Decision

Synthetic last-tick feed only — fixed fields, scaled ints, random walk with seed 42, config-driven symbols/rate, server-side TickGenerator + poll broadcast. Rejected: ORDER/ACK, order book, matching engine.

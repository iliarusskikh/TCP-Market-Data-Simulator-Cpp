RAII { Socket fd ownership }

Every listen, accept, and connect fd is owned by SocketGuard in socket_guard.hpp. Higher-level types like ClientSession compose it with Rule of Zero — no hand-written destructors.

01

Core idea

RAII ties a resource's lifetime to an object's lifetime. For sockets: construct → own an int fd; destroy → call close(). C++ runs destructors on scope exit (including early return), so cleanup is not a separate checklist at every exit path.

Scope for this project

TICK + HEARTBEAT over TCP. One thread, poll() + non-blocking sockets. The RAII story here is fd ownership, not mutex locking.

02

SocketGuard

SocketGuard in include/socket_guard.hpp is a move-only owner of a POSIX socket fd.

include/socket_guard.hpp 
class SocketGuard {
public:
    explicit SocketGuard(int fd) noexcept : fd_(fd) {}
    ~SocketGuard() { reset(); }

    int get() const noexcept { return fd_; }
    bool valid() const noexcept { return fd_ >= 0; }
    void reset(int fd = -1) noexcept;  // close old, adopt new (or -1)
    int release() noexcept;            // relinquish without closing

    SocketGuard(const SocketGuard&)            = delete;
    SocketGuard& operator=(const SocketGuard&) = delete;
    SocketGuard(SocketGuard&&) noexcept;
    SocketGuard& operator=(SocketGuard&&) noexcept;
private:
    int fd_{-1};
};

Move-only: copy is deleted so two guards cannot own the same fd. Move steals the fd and sets the source to -1 so the moved-from destructor is a no-op.

Decision

RAII for every fd. Rejected: bare int + manual close() on every error path — too easy to leak or double-close as session management grows.

04

Rule of Zero vs Five

  • Rule of Five — a type that owns a raw resource (like SocketGuard) needs destructor + copy/move ctor + copy/move assign defined together. Default shallow copy would double-close.
  • Rule of Zero — prefer writing none of those on higher-level types. Hold a SocketGuard (and vector, etc.) as members; compiler-generated special members then do the right thing.
client_session.hpp (Rule of Zero) 
struct ClientSession {
    SocketGuard sock;           // owns the fd
    std::vector<char> out;      // pending wire bytes
    size_t out_off = 0;
    bool alive = true;
    // no hand-written dtor / copy / move
};

When a dead session is dropped from the server's clients vector, ClientSession's destructor runs → SocketGuard closes the fd automatically.

05

Project decision

Decision

SocketGuard everywhere; Rule of Zero for session types. The single-threaded poll() loop adds and removes clients dynamically — RAII guarantees exactly-one close when a peer drops mid-parse or a session is erased from the vector. Rejected: raw fd + scattered close() calls.

06

Pitfalls

✕

Double-close

If copy is allowed (or move fails to null the source), two destructors call close() on the same number. The second close may hit an unrelated fd the kernel already reused.

✕

Escaping the raw fd

get() is fine for a same-scope send/recv/poll call. Storing that int elsewhere (or calling close() yourself while the guard still owns it) breaks the ownership model.

✕

Manual close + guard

Once wrapped, do not also close(guard.get()) on error paths. Use guard.reset() or let scope exit handle it — not both.
